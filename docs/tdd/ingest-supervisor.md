# Task 4 — ingest-supervisor

## Raw request

Держать процесс ffmpeg живым: перезапускать с экспоненциальным backoff, всегда с
`resume` и корректно вычисленным `start_number`, и вести себя по-разному при отказе
аутентификации и сетевом отказе.

## Spec

### Facts

- Проект greenfield. Python 3.14.4, тесты — `.venv/bin/pytest`.
- **Этот компонент существует по внешней причине, а не по вкусу:** у ffmpeg нет
  автореконнекта для RTSP — флаги `-reconnect*` документированы только для
  протокола `http` [VERIFIED, ffmpeg `protocols.texi`]. `-rtsp_transport tcp`
  задаёт только транспорт и никакого поведения при обрыве не добавляет.
- Камера из §7 при проверке отвечала `401` при живом TCP-порте — то есть состояние
  «сеть есть, креды не подходят» реально и требует отдельной обработки.

### Decisions (связывают эту задачу)

- **D7** — глубина DVR равна всей сессии, поэтому перезапуск **обязан** сохранять
  уже накопленную историю. Это главное требование к этой задаче.
- **D8** — кодек определяется на старте (Task 3), результат передаётся в
  сборку argv (Task 1).
- **D1** — источник берётся из конфигурации.

### Assumptions

- **[A1]** Первый запуск в сессии идёт с `resume=False`; **любой последующий —
  с `resume=True`** и `start_number = next_start_number(spool)`. Голый
  `append_list` без явного `start_number` считается дефектом (см. [A1] в
  `hls-command-builder.md`).
- **[A2]** Проба кодека (Task 3) выполняется перед **первым** запуском. При
  перезапусках она не повторяется, если только предыдущий отказ не был `CODEC`.
- **[A3]** Backoff экспоненциальный от небольшого начального значения с потолком
  `max_backoff` (по умолчанию 30 с).
- **[A4]** При `FailureKind.AUTH` применяется заметно более длинный интервал
  повтора, чем при `NETWORK`: неверные креды повтором не лечатся, а частые попытки
  на Hikvision-прошивках приводят к блокировке учётной записи — это наблюдалось
  в этой самой сессии при проверке §7.

### Критерии готовности — чеклист, тестов не пишем

**Режим: без тестов** (решение D11). Тест здесь мокал бы `subprocess` и `sleep`
и проверял структуру собственных моков, а не то, перезапускается ли ffmpeg на
самом деле. Проверяется запуском: убить процесс ffmpeg и посмотреть, поднялся ли
он и продолжилась ли нумерация сегментов. Канал до камеры уже показал потери —
случай представится сам.

`src/ingest/supervisor.py`:

1. Первый вызов сборки argv происходит с `resume=False`.
2. После падения процесса следующий вызов идёт с `resume=True` **и**
   `start_number`, полученным из спула, а не с нулём.
3. Backoff растёт экспоненциально между последовательными падениями.
4. Backoff не превышает `max_backoff`.
5. После успешной длительной работы backoff сбрасывается к начальному значению.
6. При stderr с `401` супервизор логирует явное сообщение про креды и применяет
   удлинённый интервал по сравнению с сетевым отказом.
7. При сетевом отказе применяется обычный backoff.
8. **Тесты не запускают настоящий ffmpeg**: запуск процесса и сон подменяются,
   тест не длится дольше долей секунды.
9. Супервизор не завершается сам при повторяющихся отказах — он продолжает
   попытки (это `NoReturn`-цикл).

### Вне scope

Сборка argv (Task 1), классификация stderr (Task 2), проба кодека (Task 3) — здесь
они только вызываются. Выгрузка в облако (Task 5) — отдельный процесс.
