# Task 5 — segment-uploader

## Raw request

Выкладывать содержимое локального спула в S3-совместимое объектное хранилище так,
чтобы плеер никогда не получил ни битого сегмента, ни плейлиста, ссылающегося на
ещё не выложенный файл.

## Spec

### Facts

- Проект greenfield. Python 3.14.4, тесты — `.venv/bin/pytest`.
- **У ffmpeg нет протокола S3** — проверен полный список из 46 протоколов, S3
  отсутствует [VERIFIED, ffmpeg `protocols.texi`]. Поэтому выгрузка обязана быть
  отдельным процессом; «один ffmpeg делает всё» невозможно.
- **R2 не поддерживает conditional PUT** (`x-amz-if-match` / `if-none-match` на
  PutObject/CopyObject) [VERIFIED, developers.cloudflare.com/r2/api/s3/api/].
  Значит идемпотентность **нельзя** строить на них.
- **R2 сохраняет Content-Type, только если задать его явно при PUT**; иначе выводит
  сам [VERIFIED, developers.cloudflare.com/r2/objects/upload-objects/]. Неверный
  Content-Type ломает воспроизведение **молча**.
- `hls_flags temp_file` заставляет ffmpeg писать в `filename.tmp` и переименовывать
  по завершении; действует и на сегменты, и на плейлисты. Документация ffmpeg прямо
  указывает, что **блокировка доступа к `*.tmp` — обязанность того, кто раздаёт**,
  а не самого флага [VERIFIED, ffmpeg `muxers.texi`].
- boto3 работает с R2 через `endpoint_url` и `region_name='auto'`
  [VERIFIED, developers.cloudflare.com/r2/get-started/s3/].

### Decisions (связывают эту задачу)

- **D2** — облако: Cloudflare R2 через S3-совместимый API. Код не должен зависеть
  от конкретного провайдера: переезд на AWS S3 или MinIO — смена конфигурации.
- **D10** — плеер читает манифест **напрямую из хранилища**, поэтому корректность
  выгрузки находится на пути показа, а не в архивной ветке.
- **D7** — удаление выгруженного из спула вне scope: EVENT копит сегменты, это
  принятый техдолг.

### Assumptions

- **[A1] Несущий инвариант:** выкладываются **только те сегменты, которые уже
  перечислены в плейлисте**. ffmpeg вносит сегмент в плейлист только закрыв его,
  поэтому «есть в плейлисте» — надёжный признак завершённости. Это одно правило
  снимает и гонку с недописанным файлом, и требование порядка выкладки.
- **[A2]** Плейлист выкладывается **последним**, после всех перечисленных в нём
  сегментов. Обратный порядок даёт 404 у плеера.
- **[A3]** Множество уже выгруженных ключей персистится в `spool/.uploaded.json`,
  иначе перезапуск процесса перезальёт всю сессию и сломает арифметику Class A.
- **[A4]** Файлы `*.tmp` не выкладываются никогда, ни при каких условиях.

### Acceptance criteria (форма падающих тестов)

`src/uploader/storage.py`, `src/uploader/sync.py`, тесты в `tests/test_uploader.py`:

1. `segments_in_playlist()` возвращает только имена сегментов, игнорируя строки
   `#EXT-…`, комментарии и пустые строки.
2. `segments_in_playlist()` на плейлисте без сегментов → пустой список.
3. **Инвариант [A1]:** сегмент, физически лежащий в спуле, но **отсутствующий** в
   плейлисте, не выкладывается.
4. **Порядок [A2]:** тест фиксирует последовательность вызовов хранилища и
   проверяет, что `index.m3u8` выложен **после** всех сегментов этого цикла.
5. Файл `seg_000009.ts.tmp` не выкладывается никогда.
6. Content-Type для `.m3u8` — ровно `application/vnd.apple.mpegurl`.
7. Content-Type для `.ts` — ровно `video/mp2t`.
8. Повторный `sync_once` без изменений в спуле не делает **ни одного** PUT
   сегмента (плейлист может перезаписываться — это допустимо и ожидаемо).
9. Новый сегмент, появившийся в плейлисте, выкладывается на следующем цикле.
10. Состояние выгрузки переживает перезапуск: после записи `.uploaded.json` и
    создания нового экземпляра ранее выгруженные сегменты повторно не выкладываются.
11. Ошибка хранилища на одном сегменте не помечает его выгруженным — на следующем
    цикле попытка повторяется.
12. **Тесты работают против фейкового хранилища; сети нет, boto3 не вызывается.**

### Вне scope

Настройка CORS и публичного доступа в бакете — это конфигурация R2, а не код
(записано в «## Codebase context», C.3). Удаление выгруженного из спула — D7.

## Implementation

**Сделано.** `src/uploader/storage.py`, `src/uploader/sync.py`,
тесты `tests/test_uploader.py` — **25 тестов**, всего по проекту 55 зелёных.

```python
segments_in_playlist(text) -> list[str]
sync_once(spool, storage, prefix, state: SyncState) -> SyncState
load_state(spool) / save_state(spool, state)
run_forever(spool, storage, prefix, interval)
content_type_for(name) -> str
S3ObjectStorage(bucket=…, endpoint_url=…, region="auto", …)
```

### Проверено на настоящем S3-сервере, не только на фейке

R2 ещё нет, поэтому поднят **MinIO в Docker** — тот же S3-совместимый API — и
аплоадер прогнан на **реальном спуле с камеры: 225 сегментов, 928 МБ**.

| Проверка | Результат |
|---|---|
| Первый проход | 225 сегментов + плейлист = 226 объектов за 7,0 с |
| `Content-Type` у `.m3u8` | `application/vnd.apple.mpegurl` ✅ |
| `Content-Type` у `.ts` | `video/mp2t` ✅ |
| Идемпотентность, второй проход | 0,00 с, ни одного нового объекта |
| Состояние переживает перезапуск | 225 ключей восстановлены, digest совпал |
| **Манифест из бакета ссылается на отсутствующие объекты** | **0 из 225** |

Последняя строка и есть несущий инвариант задачи, проверенный на боевых данных.

### Отклонения от исходной спецификации

- **Сигнатура `sync_once` принимает `SyncState`, а не `set[str]`.** Кроме
  множества выгруженных ключей нужен ещё digest плейлиста — см. следующий пункт.
- **Плейлист перезаливается только при изменении содержимого.** Спецификация это
  разрешала («плейлист может перезаписываться»), но при `upload_interval=1 с` это
  дало бы 3600 операций записи в час на один только плейлист. По digest выходит
  ~900/час — вчетверо меньше. При квоте R2 в 1 млн Class A разница осязаема.
- **Плейлист придерживается, пока хоть один его сегмент не в бакете.** Этого в
  спецификации не было: там требовался лишь порядок «сегменты раньше плейлиста».
  Но при сбое загрузки одного сегмента порядок сам по себе не спасает —
  опубликованный манифест сослался бы на 404. Теперь при неполной выгрузке
  плейлист не публикуется вовсе и повторяется на следующем цикле.
- **Сегмент, перечисленный в плейлисте, но ещё не читаемый с диска**, тоже
  придерживает плейлист.
- Битый `.uploaded.json` не роняет аплоадер: состояние сбрасывается, что стоит
  повторных загрузок, но не корректности.

### Параллельная выгрузка — добавлено после замера на живом потоке

Последовательная выгрузка держала манифест на **100–160 с** позади живого края,
хотя ffmpeg отставал всего на 3–7 с. Причина не в полосе: один PUT сегмента на
120 КБ занимает **0,67 с**, из которых передача — малая часть, остальное время
оборота до Cloudflare. При 120 КБ за 0,67 с это 1,4 Мбит/с из доступных 5–6 —
канал простаивал на три четверти.

`sync_once` получил пул на 8 потоков (`UPLOAD_WORKERS`), пул соединений botocore
поднят до `workers * 2` — иначе потоки сериализуются на соединениях и
параллельность не даёт ничего.

| | Последовательно | Параллельно, 8 |
|---|---|---|
| Отставание манифеста | 100–160 с | **20–49 с** |
| Разрыв диск→R2 | 18–40 сегментов | 3–11 |

**Инвариант не изменился.** Порядок между сегментами и раньше не имел значения:
читать их некому, пока не опубликован плейлист, а он публикуется только когда все
перечисленные в нём сегменты уже в бакете. Параллельность трогает лишь порядок
внутри группы, которая целиком невидима до публикации.

Шесть новых тестов, из них один сторожевой: `SlowStorage` считает пиковую
одновременность, так что молчаливый возврат к последовательной выгрузке уронит
сборку. Всего по проекту 63 теста.

### Автоочистка спула

Спул рос без ограничений: выгруженные сегменты оставались на диске навсегда. Их
никто не читает — плеер ходит в бакет, — поэтому через `SPOOL_RETENTION` секунд
(по умолчанию 300) они удаляются. Проход раз в 30 с, а не каждый цикл выгрузки:
это обход каталога.

Удаляется только то, что лежит в `state.uploaded` — единственное свидетельство,
что сегмент действительно долетел. Никогда не удаляются плейлист, `.uploaded.json`,
`*.tmp` и **самый свежий выгруженный сегмент**.

Последнее — не перестраховка, а защита от потери записи. При отсутствующем
плейлисте `next_start_number()` берёт наибольший индекс с диска; пустой спул дал
бы старт с нуля и перезапись уже выложенной истории. Удаляются только младшие
индексы, поэтому верхняя граница нумерации не опускается никогда.

Проверено на боевом томе: **487 → 57 сегментов, удалено 437**, что ровно
соответствует окну в 300 с при сегментах по 5 с. При этом манифест в бакете
перечисляет 498 сегментов, отсутствующих — ноль, а `seg_000000.ts`, стёртый с
диска, продолжает отдаваться из R2 с кодом 200: история цела.

Двенадцать новых тестов, каждый — на отдельный способ потерять запись. Всего по
проекту 106 тестов.
