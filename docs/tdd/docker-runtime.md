# Task 8 — docker-runtime

## Raw request

Собрать и запустить всю систему одной командой, с ffmpeg внутри образа, и написать
README.

## Spec

### Facts

- Проект greenfield: ни `Dockerfile`, ни `docker-compose.yml`, ни `.env.example`
  не существует.
- **В хосте нет ни `ffmpeg`, ни `ffprobe`, ни `node`/`npm`** — всё, что нужно
  рантайму, обязано приехать в образе.
- ⚠️ **`docker` в текущем WSL-дистрибутиве недоступен**: «The command 'docker'
  could not be found in this WSL 2 distro… activate WSL integration in Docker
  Desktop». Требуется включить WSL-интеграцию в Docker Desktop — **действие
  пользователя**, вне контура этой задачи. До этого задача не проверяема.
- Креды камеры (§7) при проверке отвергнуты, и лежат открытым текстом в файле ТЗ
  внутри рабочей папки.

### Decisions (связывают эту задачу)

- **D4** — запуск в Docker, ffmpeg ставится в образ.
- **D1** — RTSP-источник и креды параметризуются через окружение и **не попадают
  в репозиторий**.
- **D2** — облако R2 через S3-совместимый API; провайдер меняется конфигурацией.
- **D10** — ngrok пробрасывает **только** веб-страницу; видео идёт из хранилища.
- **D7** — ротация EVENT-плейлиста описана, но не реализуется; это техдолг,
  который надо назвать в README, а не умолчать.

### Assumptions

- **[A1]** Три сервиса: `ingest`, `uploader`, `web`. Спул — общий том между
  `ingest` и `uploader`.
- **[A2]** Один общий образ на все три сервиса, различающиеся командой запуска —
  проще, чем три почти одинаковых образа.
- **[A3]** Для разработки предусмотрен локальный RTSP-источник (D1), чтобы тракт
  можно было проверить без камеры из §7.

### Критерии готовности — чеклист, тестов не пишем

**Режим: без тестов** (решение D11). Это интеграция: проверяется тем, что всё
поднимается и работает.

1. `docker compose up` поднимает `ingest`, `uploader`, `web`; спул виден обоим
   процессам, которым он нужен.
2. В образе присутствуют работающие `ffmpeg` и `ffprobe` — проверяется на этапе
   сборки, а не в рантайме.
3. `web` отвечает 200 на `/healthz` после подъёма.
4. `.env.example` содержит **только имена** переменных, без единого значения.
   Реальный `.env` — в `.gitignore`.
5. В репозитории **нет** ни адреса камеры, ни пароля из §7, ни ключей хранилища.
6. При отсутствии обязательной переменной окружения сервис падает на старте с
   внятным сообщением, а не работает молча наполовину.
7. Поднимается локальный RTSP-источник для разработки, и на нём тракт
   «ingest → спул → плеер» проходит целиком.

### README обязан описать

- Как запустить, какие переменные окружения нужны.
- **Где именно измеряется задержка** (D5) и почему выбрана такая точка — §2 в ТЗ
  точку не задаёт, и это надо назвать явно.
- Известные ограничения, без смягчения:
  - расхождение часов браузера и источника искажает замер задержки;
  - EVENT-плейлист копит сегменты бесконечно, ротация не реализована (D7);
  - `r2.dev` официально «intended for non-production traffic» и rate-limited;
  - **креды камеры из §7 проверить не удалось** — `DESCRIBE` возвращает 401 при
    живом TCP-порте; кодек, разрешение и путь потока остались неизвестны, поэтому
    кодек определяется в рантайме (D8).
- Почему выбран обычный HLS, а не WebRTC/LL-HLS: бюджет §2 в 2 минуты, и единый
  EVENT-манифест — единственный проверенный способ дать §5 и §6 «одновременно».

### Вне scope

Настройка аккаунта R2, CORS и публичного доступа — это клики в панели Cloudflare,
описанные в «## Codebase context», C.3. Установка ngrok.

## Implementation

**Сделано.** `deploy/Dockerfile` (один образ на три сервиса), `docker-compose.yml`,
`README.md`, `.env.example`, `deploy/r2-cors.json`, `.gitignore`.

### Один образ вместо трёх

Первая версия имела `Dockerfile.web` с `FROM bigbro-ffmpeg:local`. Это дефект:
**compose не гарантирует порядок сборки сервисов**, поэтому на чистой машине сборка
веба могла начаться раньше, чем появится образ, от которого она наследуется.
Три отдельных образа тоже плохи — три загрузки одной и той же базы по узкому каналу.
Итог: один образ, три команды, якорь `x-app` в compose.

### Политика перезапуска действительно заменяет супервизор (задача 4)

**Первый тест был неверным.** `docker compose kill ingest` дал `RestartCount=0`, и
я поначалу счёл заявление опровергнутым. Код выхода 137 — SIGKILL от самого
Docker; такую остановку он считает намеренной и политику не применяет. Это
свойство теста, а не системы.

Правильный тест — убить ffmpeg **внутри** контейнера, чтобы процесс завершился сам:

| | |
|---|---|
| `RestartCount` после падения | **1**, состояние `running` |
| `seg_000000` | цел |
| Нумерация | 0…79 без разрывов |
| Дубликаты | 0 |

То есть `resume_start_number()` из задачи 1 отрабатывает и в боевой топологии, а
отдельный процесс-супервизор не нужен.

### Как не ждать при проверках

- `HLS_TIME=1` вместо 4 — сегменты появляются вчетверо чаще. При `-c copy` это
  **пол, а не цель**: короче интервала между ключевыми кадрами не получится.
- Опрашивать задержку раз в 10–15 с, а не раз в минуту — величина меняется чаще.
- Состояние контейнера смотреть через `docker inspect`, а не циклом ожидания:
  `RestartCount`, `State.ExitCode` и политика доступны мгновенно.
