# Task 7 — dvr-player-page

## Raw request

Страница с плеером, который **одновременно** показывает лайв-трансляцию и даёт
перематывать её по всей накопленной истории, плюс показывает числом текущую
задержку.

## Spec

### Facts

- Проект greenfield. **`node` и `npm` в окружении отсутствуют** — сборки фронтенда
  быть не может, `hls.js` кладётся файлом в репозиторий.
- `#EXT-X-PLAYLIST-TYPE:EVENT`: сервер «MUST NOT change or delete any part of the
  Playlist; MAY append lines» — плейлист только растёт [VERIFIED, RFC 8216].
  Отсюда у плеера **одна полоса, покрывающая всю историю и live-край**.
- hls.js: `liveDurationInfinity` выставляет длительность MediaSource в Infinity;
  `liveSyncDuration`/`liveSyncDurationCount` задают отступ от live-края;
  `hls.liveSyncPosition` даёт точку синхронизации [VERIFIED, hls.js `docs/API.md`].
- `backBufferLength` — **контроль памяти, а не диапазон полосы перемотки**.
  Диапазон задаётся `totalduration` плейлиста [VERIFIED, hls.js `docs/API.md`].
- ⚠️ **`frag.programDateTime` существует в исходниках, но отсутствует в
  `docs/API.md`.** В `src/loader/fragment.ts` у `Fragment` есть
  `rawProgramDateTime: string | null` (ISO 8601) и геттер `programDateTime`,
  парсящий его через `Date.parse()` — то есть **epoch в миллисекундах**
  [VERIFIED, прямая выгрузка исходника]. Связка `Hls.Events.FRAG_CHANGED` →
  `data.frag.programDateTime` подтверждается тредами issue-трекера, но это
  **недокументированный публичный API**.
- ⚠️ **Нативный HLS в Safari ненадёжен для перемотки назад**: сторонние
  баг-репорты о пропаже полосы прокрутки и рестарте с нуля [UNVERIFIED, не
  первоисточник Apple, но риск реальный].

### Decisions (связывают эту задачу)

- **D6** — один EVENT-манифест: лайв и история из одного источника, никакой
  стыковки двух потоков.
- **D5** — задержка = `Date.now()` − (`EXT-X-PROGRAM-DATE-TIME` сегмента +
  смещение внутри сегмента), выводится **числом на страницу**.
- **D7** — глубина перемотки равна всей сессии.
- **D10** — манифест тянется напрямую из объектного хранилища.

### Assumptions

- **[A1]** hls.js форсируется **и в Safari тоже**, а не отдаётся нативному HLS —
  иначе §6 под угрозой.
- **[A2]** Часы браузера и источника считаются приблизительно синхронными.
  Расхождение искажает замер D5 — это **известное ограничение**, которое надо
  записать в README, а не прятать.

### Acceptance criteria

**Шаг 0, обязателен первым.** Проверить связку `Hls.Events.FRAG_CHANGED` →
`data.frag.programDateTime` на реальном hls.js. Если она не подтвердится —
перейти на запасной путь: самостоятельно парсить `#EXT-X-PROGRAM-DATE-TIME` из
загруженного манифеста. Далее:

1. Полоса перемотки покрывает **всю историю с начала сессии**, а не последние
   N секунд. Проверяется на манифесте EVENT с заведомо большим числом сегментов.
2. Перемотка назад в середину истории работает, и после неё воспроизведение
   продолжается, а не встаёт.
3. Кнопка «К эфиру» переводит `currentTime` на `hls.liveSyncPosition`.
4. На странице виден числовой показатель задержки в секундах, и он обновляется
   по мере воспроизведения.
5. Виден индикатор состояния «в эфире» против «отстал на N секунд».
6. hls.js используется во всех браузерах, включая Safari; нативный HLS не
   задействуется.
7. `hls.js` подключается локальным файлом из репозитория, без CDN и без сборки.
8. Ошибка загрузки манифеста (404, CORS) показывает **внятное сообщение на
   странице**, а не пустой чёрный прямоугольник — это два самых вероятных отказа
   при неверно настроенном бакете.

### Замечание про тесты

**Режим: без тестов** (решение D11). Браузерную часть проверяют глазами: играет
или не играет, перематывается или нет. Расчёт задержки и определение «отстал / в
эфире» всё равно стоит вынести в отдельные чистые функции — но ради читаемости и
возможности проверить их в консоли, а не ради тестов.

### Вне scope

Маршруты и резолвинг пути (Task 6).

## Implementation

**Сделано.** `src/web/static/player.js`, перерисованные `watch.html` и `style.css`,
`src/web/static/vendor/hls.js` (530 КБ, в репозитории).

Чистые функции вынесены, как и просила спецификация: `latencySeconds(anchor,
currentTime, now)` и `liveState(behindSeconds, threshold)` — обе без побочных
эффектов, проверяются из консоли.

| Критерий | Состояние |
|---|---|
| 1. Полоса на всю историю | `liveDurationInfinity: true`, диапазон из плейлиста |
| 2. Перемотка назад | ✅ подтверждено в браузере на живом потоке |
| 3. Кнопка «К эфиру» | `hls.liveSyncPosition`, откат на `seekable.end` |
| 4. Числовая задержка | `frag.programDateTime` + смещение, обновление раз в 0,5 с |
| 5. Индикатор «в эфире» | порог 12 с, зелёный цвет и блокировка кнопки |
| 6. hls.js везде | нативный HLS не задействуется вовсе |
| 7. Локальный файл | ✅ отдаётся как `text/javascript`, проверено curl |
| 8. Внятная ошибка | отдельные тексты для 403, 404, CORS и ошибки разбора |

### Отклонения и находки

- **`backBufferLength: 900`** добавлен сверх спецификации — это ограничение
  памяти, а не диапазона перемотки. Без него многочасовая сессия в браузере
  растёт неограниченно.
- **Фатальные ошибки не сразу показываются пользователю**: медиа-ошибка сначала
  проходит через `recoverMediaError()`, сетевая (кроме загрузки манифеста) — через
  `startLoad()`. На страницу выводится только то, что не восстановилось.
- **Записанный кусок на 225 сегментов для проверки лайв-части не годится**: в его
  плейлисте есть `#EXT-X-ENDLIST`, hls.js видит его как VOD. Критерии 3–5
  проверяются только на живом потоке — так они в итоге и проверялись.
- `frag.programDateTime` читается через проверку типа: недокументированный API,
  при его пропаже показывается «—», а не падение.
