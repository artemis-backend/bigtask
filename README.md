# RTSP → облако → браузер с перемоткой

Трансляция с IP-камеры уезжает в объектное хранилище растущим HLS-плейлистом, а
веб-страница показывает её так же, как YouTube показывает прямой эфир: **живой
край и вся накопленная история на одной полосе перемотки**.

Замерено на боевом стеке: отставание живого края **5–13 секунд** при бюджете в
две минуты, глубина перемотки — вся сессия с момента запуска.

---

## Запуск

Нужны Docker с плагином compose и бакет в S3-совместимом хранилище.

### 1. Хранилище

Подойдёт любое S3-совместимое — код провайдер-агностичен. Для Cloudflare R2:

1. `R2 Object Storage` → включить (попросит платёжные данные даже для
   бесплатного уровня).
2. Создать бакет.
3. `Manage R2 API Tokens` → `Create API Token` → **Object Read & Write**,
   область — только этот бакет. Ключи показываются **один раз**.
4. Бакет → `Settings` → включить публичный доступ через `r2.dev`. Без этого
   плеер не прочитает манифест: токен в браузер не отдаётся.
5. Там же `CORS Policy` → вставить [`deploy/r2-cors.json`](deploy/r2-cors.json).
   **Без CORS манифест загрузится и молча не заработает.**

Публичный доступ включается не мгновенно — первый запрос может вернуть 403.

### 2. Конфигурация

```bash
cp .env.example .env
```

Заполнить `RTSP_URL`, `S3_*` и `PUBLIC_BASE_URL`. Минимум:

```ini
RTSP_URL=rtsp://ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ@62.64.17.113:2554
RTSP_PATH=/Streaming/Channels/102
S3_BUCKET=имя-бакета
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_ENDPOINT_URL=https://<account-id>.r2.cloudflarestorage.com
PUBLIC_BASE_URL=https://pub-<hash>.r2.dev
STREAM_ID=demo
```

`.env` в `.gitignore` и в репозиторий не попадает.

### 3. Старт

```bash
docker compose up --build
```

Открыть **<http://localhost:8000>** и нажать «Смотреть».

Поле «путь до трансляции» подставляется само: страница спрашивает у сервиса его
`STREAM_ID` и предлагает его. Ввести можно и что угодно другое — в том числе
готовый адрес манифеста, и тогда веб-сервис не нужен вовсе.

Важно понимать, что **веб-сервис не знает, что именно пишет `ingest`**. Он лишь
собирает `PUBLIC_BASE_URL` + введённый путь + `index.m3u8` и отдаёт этот адрес
плееру. Подсказка на странице — единственное, что связывает его с `STREAM_ID`.

### Проверить, что всё живо

```bash
docker compose ps                     # три сервиса в состоянии Up
docker compose logs -f uploader       # выгрузка в бакет
curl -s localhost:8000/healthz        # {"status":"ok"}
curl -s "localhost:8000/api/resolve?src=demo"   # адрес манифеста
```

Первые сегменты появляются через 10–20 секунд после старта: плейлист публикуется
только когда все перечисленные в нём сегменты уже лежат в бакете.

Остановить — `docker compose down`. Добавить `-v`, чтобы стереть и накопленную
запись.

### Пересборка после правок

Все три сервиса собраны из одного образа, поэтому **пересборка одного из них
останавливает остальные два**: compose видит, что они запущены из устаревшего
образа. Трансляция при этом прерывается молча — в логах ничего не появится.

```bash
docker compose up -d --build web   # ⚠️ ingest и uploader уйдут в Exited
docker compose up -d --build       # так правильно: поднимутся все три
```

Если это всё же случилось, `docker compose up -d` возвращает всё на место.
Накопленная запись не теряется: спул лежит в именованном томе, а нумерация
сегментов продолжается с прежнего места.

## Как это работает

```
камера ──RTSP/TCP──> ffmpeg ──> спул в томе ──> uploader ──S3──> хранилище
                                                                     │
                                 браузер <── hls.js <── манифест ─────┘
```

| Сервис | Что делает |
|---|---|
| `ingest` | ffmpeg тянет RTSP и режет в HLS-сегменты с `#EXT-X-PLAYLIST-TYPE:EVENT` |
| `uploader` | выкладывает сегменты и плейлист в хранилище, восемью потоками |
| `web` | отдаёт страницу с плеером и превращает «путь до трансляции» в адрес манифеста |

**Видео через веб-сервис не проходит.** Плеер тянет сегменты напрямую из
хранилища; сервис нужен только для страницы и разбора пути. Поэтому нагрузка на
него не зависит от числа зрителей.

### Почему живой эфир и перемотка получаются одновременно

Это единственное нетривиальное решение во всей системе.

По RFC 8216 в плейлист типа `EVENT` разрешено только **дописывать** строки;
удалять нельзя. Значит один и тот же манифест содержит и первый сегмент сессии,
и последний. Плееру не нужно склеивать «архив» и «эфир» из двух источников —
одна полоса покрывает всю сессию сама собой, ровно как на YouTube.

Отсюда же следует и цена: плейлист растёт всю сессию и ничего не удаляет.

### Порядок публикации

Сегменты выкладываются **только после того, как ffmpeg внёс их в плейлист** —
это признак, что файл дописан. Сам плейлист выкладывается **последним и только
когда все перечисленные в нём сегменты уже в бакете**. Иначе зритель получил бы
манифест со ссылками на 404.

### Перезапуск после сбоя

Своего реконнекта для RTSP у ffmpeg нет, поэтому супервизором работает политика
`restart: unless-stopped`. При падении контейнер поднимается сам, а нумерация
сегментов продолжается с прежнего места — накопленная история не затирается.
Проверено: после убийства ffmpeg нумерация 0…79 без разрывов и дубликатов.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `RTSP_URL` | адрес камеры с учётной записью |
| `RTSP_PATH` | путь к субпотоку; пусто — основной поток |
| `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | доступ к бакету |
| `S3_ENDPOINT_URL` | `https://<account>.r2.cloudflarestorage.com`; для MinIO — `http://localhost:9000` |
| `PUBLIC_BASE_URL` | публичный адрес бакета, из него собирается ссылка на манифест |
| `STREAM_ID` | префикс в бакете и одновременно «путь до трансляции» |
| `HLS_TIME` | целевая длина сегмента, с (по умолчанию 4) |
| `SPOOL_DIR` | каталог спула внутри контейнера; compose задаёт его сам |
| `UPLOAD_INTERVAL` | пауза между проходами выгрузки, с (по умолчанию 1) |
| `UPLOAD_WORKERS` | сколько сегментов выгружать одновременно (по умолчанию 8) |
| `TRANSCODE`, `VIDEO_BITRATE`, `SCALE_HEIGHT` | включают перекодирование вниз; любая из трёх достаточна |

При `-c copy` (то есть без перекодирования) `HLS_TIME` — **пол, а не цель**:
ffmpeg режет только по ключевым кадрам, короче интервала между ними сегмент не
получится.

## Что стоит знать заранее

**Аплинк должен быть шире потока камеры.** Основной поток камеры из задания —
9,2 Мбит/с, субпоток на `/Streaming/Channels/102` — 553 кбит/с. По умолчанию
берётся субпоток: он влезает в узкий канал без перекодирования и позволяет
оставить `-c copy`, то есть не тратить процессор вовсе. Для камеры без субпотока
есть `VIDEO_BITRATE` — он включает перекодирование вниз ценой процессорного
времени. Если канал уже потока, выгрузка отстаёт от реального времени
безвозвратно, и настройками плеера это не лечится.

**Метки времени берутся из момента прихода пакета**, а не из заявленной камерой
частоты кадров. Эта камера заявляет 20 fps и отдаёт около пяти; с флагом `genpts`
медиавремя шло бы втрое медленнее настенных часов, и живой край уползал бы без
предела.

**Замер задержки опирается на часы браузера.** Он считается как разница между
`Date.now()` и меткой `EXT-X-PROGRAM-DATE-TIME` играющего сегмента. Расхождение
часов зрителя и машины с ffmpeg целиком переходит в показанную цифру.

**Хранилище расходуется линейно и не освобождается.** На субпотоке это около
80 МБ в час, на основном потоке — 3,9 ГБ в час. На бесплатных 10 ГБ в R2 это
примерно сорок часов и два с половиной часа соответственно.

**hls.js используется во всех браузерах, включая Safari.** Нативный HLS не
задействуется намеренно: его поведение при перемотке назад по EVENT-плейлисту
ненадёжно.

## Разработка

Для тестов Docker не нужен — достаточно `pytest`:

```bash
python3 -m venv .venv          # или: uv venv
.venv/bin/pip install pytest   # или: uv pip install pytest
.venv/bin/pytest               # 63 теста
```

boto3, fastapi и uvicorn ставить не требуется: тесты работают против фейкового
хранилища, а boto3 импортируется лениво — только когда действительно создаётся
клиент. Проверено на чистом клоне репозитория.

Тестами покрыты две вещи, где ошибка тихая и дорогая: сборка аргументов ffmpeg
(нумерация сегментов при перезапуске) и выгрузка (порядок публикации, из-за
которого плеер может получить манифест со ссылками на несуществующие объекты).
Браузерная часть проверяется глазами.

Найти субпоток на незнакомой камере:

```bash
.venv/bin/python scripts/probe_substreams.py
```

Перебирает типовые пути, показывает разрешение и **измеренный** битрейт каждого.
Учётку из `.env` не печатает.

Спецификации задач, замеры и обоснования решений — в [`docs/tdd/`](docs/tdd/).
